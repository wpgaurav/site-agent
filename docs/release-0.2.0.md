# Site Agent 0.2.0

Makes code changes recoverable and errors actionable, makes going live an explicit decision, and fills the publishing and file-tool gaps found in the 0.1.5 audit. Access defaults are unchanged: everything starts disabled, every tool group is a separate opt-in, and authentication remains native Application Passwords.

PHP changes now pass three checks. The tokenizer reports syntax errors with their line. A PHP command-line binary matching the running major.minor version, found automatically or set with `SITE_AGENT_PHP_BINARY`, compile-checks the file, which catches errors the tokenizer accepts, such as redeclared functions, a misplaced `strict_types` declaration or an abstract method in a concrete class. After the write, Site Agent loads the front end, `admin-ajax.php` and the MCP route with WordPress's edit-scrape key, as the core plugin editor does, and reverts the change if it causes a fatal error. Must-use plugins load before scraping starts, so a server error counts as fatal for `mu-plugins/`. An unreachable site keeps the change and reports `health: unverified`. The same rollback applies to the new delete-file and move-file tools. PHP execution rejects `exit` and `die`, turns `wp_die()` into a tool error, and reports an indirect exit or fatal error as a tool error with an audit row instead of an empty response. All error results include the underlying message and line.

Edits to published, private or scheduled posts are saved as the user's autosave unless the call passes `status`; scheduling requires a future `date_gmt`. Titles are no longer passed through `sanitize_text_field()`, so text such as `<head>` and `%20` survives. Content writes accept terms (IDs or names), a featured image, slug, publish date and allowlisted meta (Rank Math or Yoast SEO fields when active, registered REST meta, and the `site_agent_post_meta_keys` filter). New tools list terms, import media from a URL or base64 data with alt text, update media metadata, create directories, and delete or move hash-matched files. `get-content` reads by URL or slug and is limited to REST-enabled post types. Listings sort by modification date. File tools include `mu-plugins/` and block credential files by name, so `tailwind.config.js` and `config/` folders are no longer hidden.

Each Application Password can be limited to a subset of the enabled groups; limited passwords do not see other tools in `tools/list`. `SITE_AGENT_ALLOW_EXECUTION` set to `false` blocks source editing, PHP and WP-CLI on a site. The audit history adds the target, Application Password name, transport and error code, and records authenticated calls that were denied. URL credentials are removed from the request and superglobals before dispatch. WP-CLI rejects `@alias` arguments, honors `SITE_AGENT_WP_CLI` and `SITE_AGENT_WP_CLI_TIMEOUT`, and receives a `PATH` and `HOME` that work under PHP-FPM. The settings page adds diagnostics, a browser Test connection button, a Settings link and per-password limits. Refused MCP requests carry an `X-Site-Agent-Auth` reason header.

Updates now use WordPress's `update_plugins_gauravtiwari.org` hook from the `Update URI` header and cache failed checks for 15 minutes. The upgrader's forced metadata refresh runs while WordPress is in maintenance mode; on gauravtiwari.org, which is also the store, that request receives HTTP 503, so earlier releases could not update themselves there. A failed forced refresh now keeps the metadata validated by the preceding update check. Sites updating 0.1.x still run the old updater, so gauravtiwari.org itself moves to 0.2.0 by direct package installation. Signed package verification is implemented but not enforced: `Updater::PUBLIC_KEY` is empty. To enforce it, run `php bin/release-key.php`, put the public key in `Updater::PUBLIC_KEY`, store the secret as `SITE_AGENT_SIGNING_KEY` outside the repository with a backup, and build with it exported; `bin/build.sh` then signs every package and refuses to build unsigned ones. Network deactivation disables every site, and uninstall removes MCP sessions and caches on every site, deleting settings, limits, audit history and the license only when that option is enabled.

Verification on a disposable WordPress 6.9 site passed 59 PHPUnit tests (383 assertions) on PHP 8.3 and 8.5, 9 converter tests, WordPress coding standards, syntax checks and the translation-template check. The HTTP smoke test passed initialization, all 16 tools, authenticated PHP and WP-CLI, strict schemas, contributor and anonymous refusal with the reason header, and a real fatal `mu-plugins` write detected through the site and reverted. A browser check confirmed diagnostics, saving a per-password limit, and Test connection reporting the limited tool count. PHP 8.0 was not run locally; CI covers it.

The companion package moves to 0.2.0, the version its build requires to match the plugin, with its tool and developer references updated for the new tools, staging, rollback and limits.
